# Summary

Fixed `text_segmenter.py`'s silent misalignment fallback — the real
correctness defect discovered during `WI-ANNOTATE-0054`'s hand-
validation, confirmed on 100% of `corpora/london` stories in that
trial.

# Result

Two root causes fixed in `lcats/src/lcats/analysis/text_segmenter.py`:

1. `build_paragraph_index` collapsed single-newline-formatted source
   text (no blank-line breaks) into one giant paragraph, forcing every
   segment's anchor search across the entire document. New
   `_effective_paragraph_splitter()` detects this and falls back to
   single-newline splitting; `paragraph_text_indexer` uses the same
   effective splitter consistently for both the model-facing markers
   and `index_meta["splitter"]`.
2. `align_segment` silently fell back to a paragraph/document bound
   when an anchor genuinely couldn't be found (widened from
   `end_exact`-only to both anchors, per its own review round) — now
   returns `None` (alignment failure) instead, and also now guards
   against a missing/wrong-typed `par_id` (previously an opaque
   `TypeError`). `segments_result_aligner` now raises `ValueError` on
   any per-segment alignment failure — deliberately all-or-nothing —
   so the failure reaches `JSONPromptExtractor.extract`'s existing
   `alignment_error` path, which was previously unreachable for this
   failure mode.

Since `extracted_output` on an alignment failure is now the raw
unaligned `{"segments": [...]}` dict (not a bare list),
`segments_result_aligner` raising before ever unwrapping it, every
caller reading it needed an `alignment_error` check — found via
systematic repo-wide grep, not just the WI's own listed
`artifacts_expected`:
- `story_processors.py` — skips semantic annotation instead of
  crashing inside `annotate_segments_with_semantics` with a confusing
  `AttributeError`.
- `run_pilot.py`'s `_segment_story` — previously didn't check
  `alignment_error` at all.
- `check_segmentation_reliability.py`'s `classify()` — found via
  pre-push self-review, not my own initial pass: without this check, a
  truthy non-empty dict fell through to `"included"` with
  `segment_count` misreporting `1`, exactly the class of silent
  misreporting this script exists to measure.
- `generate_sample_segment.py` — also found via self-review; now
  raises a clear `RuntimeError` instead of crashing inside
  `_pick_segment`.

Ran a pre-push `/lrh-self-review` diff-mode pass (cold subagent, full
diff + WI orientation). It found 2 real, verified findings (the two
additional missed callers above) and one low-severity docstring
precision note (fixed) — independently re-verified both real findings
myself against the actual code (traced `check_segmentation_reliability
.py`'s `classify()`/`segment_count` computation, reproduced the exact
`AttributeError` mechanism in `generate_sample_segment.py`) before

Deterministic regression tests replay the exact recorded segment
metadata from `WI-ANNOTATE-0054`'s 3 real trial cases (`love_of_life`,
`story_of_keesh`, `brown_wolf`) against the real `corpora/london`
story text — an intentional, narrow, documented exception to this
project's test-isolation convention (`gather_promote_e2e_test.py`'s
"never depend on real data/corpora/" rationale), justified since these
are permanently-committed regression-evidence files, not generic
corpus fixtures. Empirically verified (not just asserted): all 3 real
cases now cleanly raise rather than silently overlap — their recorded
`par_id`s were generated against the old, buggy single-paragraph
indexing and no longer resolve against the fixed, correctly
multi-paragraph indexing, which is itself confirmed separately
(798/326/668 real paragraphs vs. the historical `n_paragraphs=1`).

Also discovered and fixed two stale pre-existing tests in
`text_segmenter_test.py` that only passed by relying on the old silent

resolved range; a missing-`par_id` case) — updated to assert the new,
